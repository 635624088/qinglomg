# AGENTS.md

## 1. 核心原则

本项目采用以下开发工作流：

* 文档驱动
* 小任务拆分
* 只读侦察优先
* 小步 TDD
* 明确验收
* 进度记录
* 严格控制修改范围
* 优先减少无效 token 消耗

Agent 的职责是：理解现有项目、制定最小方案、执行小任务、补充测试、运行验证、更新进度。

Agent 不应自由扩大需求范围，也不应在需求不明确时直接实现。

---

## 2. 输出语言规则

* 默认所有回复、分析、总结、文档、注释说明均使用中文。
* 除非用户明确要求英文，否则不要使用英文回复。
* 代码、命令、文件名、接口名、变量名、错误日志、第三方库名称保持原文。
* 技术术语可以保留英文，但必须配合中文解释。
* 生成 `spec.md`、`tasks.md`、`acceptance.md`、`progress.md`、`notes.md` 等开发文档时，默认使用中文。
* commit message 可以使用英文规范格式，例如 `feat(scope): message`，但任务说明和风险说明必须使用中文。

---

## 3. 工作边界

默认遵守以下限制：

* 不要无目的全仓库扫描。
* 不要无关重构。
* 不要无关格式化。
* 不要修改无关文件。
* 不要升级依赖，除非任务明确要求。
* 不要自动 push、merge、rebase。
* 不要删除用户未要求删除的文件。
* 不要伪造测试结果。
* 不要降低验收标准。
* 不要把临时调试代码留在最终提交中。
* 不要把密钥、token、cookie、`.env` 内容写入代码或文档。
* 不要把本地绝对路径写入代码。
* 不要在未确认影响范围前修改数据库、权限、鉴权、支付、删除、导入导出等高风险逻辑。

如果必须扩大修改范围，先停止并说明原因。

---

## 4. 新需求流程

当用户提出以下类型任务时，不要直接实现：

* 新功能
* 复杂 bug
* 跨文件修改
* 业务流程调整
* 数据处理流程
* 接口改造
* UI 行为变化
* 架构或模块调整
* 不明确的大需求

应先创建或更新需求目录：

```text
docs/specs/<YYYY-MM-DD-feature-name>/
├─ spec.md
├─ tasks.md
├─ acceptance.md
├─ progress.md
└─ notes.md
```

新需求默认状态为：

```text
Status: Draft
```

Draft 阶段只允许：

* 整理需求
* 只读侦察代码
* 定位相关文件
* 理解当前实现
* 提出最小改动方案
* 提出测试方案
* 拆分任务
* 记录风险和不确定点

Draft 阶段禁止修改业务代码。

只有用户明确确认后，才能将状态改为：

```text
Status: Frozen
```

Frozen 后才允许进入实现。

## 5. 文档职责

每个需求目录中的文档职责如下：

### spec.md

用于记录需求基准，包括：

* 背景
* 目标
* 非目标
* 用户流程
* 业务规则
* 技术约束
* 验收标准摘要
* 风险点

Frozen 后默认不要修改 `spec.md`。

如果发现 spec 有问题，先写入 `notes.md`，不要直接改 Frozen 状态的 `spec.md`。

### tasks.md

用于记录可执行任务。

要求：

* 每个 Task 都必须能独立执行。
* 每个 Task 都必须有明确目标。
* 每个 Task 都必须有验收方式。
* 不要把多个大任务合并成一个 Task。

### acceptance.md

用于记录验收标准和验收结果。

要求：

* 自动验收和人工验收分开写。
* 已验证、未验证、失败项必须区分清楚。
* 不要把未验证项目标记为通过。
* 不要为了通过验收而降低标准。

### progress.md

用于记录开发进度。

每次执行任务后必须更新：

* 执行日期
* 当前 Task
* 已修改文件
* 已运行命令
* 测试结果
* 当前结论
* 下一步

### notes.md

用于记录：

* 不确定点
* 风险点
* 环境问题
* 测试缺口
* 需要用户确认的问题
* 后续建议

---

## 6. 实现流程

实现任何任务前，必须先读取当前需求目录中的：

1. `spec.md`
2. `tasks.md`
3. `acceptance.md`
4. `progress.md`
5. `notes.md`

实现时必须遵守：

* 每次只执行一个 Task。
* 先测试，后实现。
* 只做满足当前 Task 的最小必要改动。
* 优先复用现有项目结构和现有代码风格。
* 不做无关优化。
* 不做无关重构。
* 不修改无关格式。
* 不引入无关依赖。
* 如果必须修改 Task 未列出的模块，先停止并说明原因。

实现后必须更新：

* `progress.md`
* `acceptance.md`
* `notes.md`，如果有风险或遗留问题

---

## 7. 代码规模与模块划分规则

- 不要为了完成需求把代码继续堆进超大文件。
- 单函数建议不超过 60 行，超过 100 行必须说明原因或拆分。
- 单业务文件建议不超过 300 行，超过 500 行必须说明原因或拆分。
- 单测试文件建议不超过 400 行，超过 700 行应按场景拆分。
- 单个小任务新增文件建议不超过 5 个，修改文件建议不超过 8 个；超过时必须先说明影响范围。
- 这些限制是维护性约束，不是机械行数要求。不要为了降低行数而拆散高度相关的逻辑。
- 自动生成文件、lockfile、快照、fixture、类型声明和静态配置可以例外。
- 已有超大文件不要默认整文件重构，只修改当前任务相关区域。
- 如果需要拆分已有超大文件，必须先说明拆分方案、影响范围和测试方式。

模块划分优先按业务能力或功能边界进行，其次再按技术层次进行。

- 一个模块只负责一个清晰业务能力或技术职责。
- 业务专属逻辑必须留在对应业务模块内。
- shared/common/core 只放真正跨业务、稳定、无业务含义的代码。
- 不要把业务逻辑随意放进全局 utils。
- 不要为了复用提前抽象。
- 不要创建职责不清的 manager、handler、processor、helper、utils。
- 不要产生循环依赖。
- 不要让低层模块依赖高层模块。
- 如果一个文件同时包含 UI、请求、业务规则、数据处理或副作用，应优先拆分。

## 8. TDD 与测试规则

默认采用小步 TDD。

### bug 修复

流程：

1. 先写能复现问题的最小回归测试。
2. 确认测试失败。
3. 做最小修复。
4. 确认测试通过。
5. 运行相关回归测试。
6. 更新 `progress.md` 和 `acceptance.md`。

### 新功能

流程：

1. 先写核心行为测试。
2. 确认当前行为缺失或测试失败。
3. 实现最小功能。
4. 确认测试通过。
5. 补充必要边界测试。
6. 更新文档和验收记录。

### 测试要求

* 优先运行与当前任务相关的测试。
* 不要默认运行全量慢测试。
* 测试失败时必须说明失败原因。
* 没有运行的测试不得声称通过。
* 如果无法自动测试，必须写清楚人工验收步骤。
* 不要通过删除测试、降低断言或跳过测试来掩盖问题。

## 9. 数据库规则

涉及数据库时，默认禁止直接执行破坏性操作。

未经明确授权，不要执行：

* DELETE
* DROP
* TRUNCATE
* 大范围 UPDATE
* ALTER TABLE
* 数据迁移
* 批量写入生产数据

数据库修改前必须先给出：

* 影响表
* 影响字段
* WHERE 条件
* SELECT 预览
* 备份方案
* 回滚方案
* 小批量验证方案

推荐流程：

1. 先写 SELECT 预览影响范围。
2. 再写备份 SQL。
3. 再写小范围验证 SQL。
4. 确认无误后再执行批量修改。
5. 修改后提供验证 SQL。

## 10. 依赖与环境规则

默认不要新增依赖。

新增依赖前必须说明：

* 为什么需要
* 是否已有替代方案
* 是否已有类似依赖
* 对构建和部署的影响
* 维护风险

默认不要升级依赖。

除非：

* spec 明确要求
* 修复安全漏洞
* 当前依赖阻塞实现
* 用户明确授权

不要为了完成小功能引入大型框架或复杂基础设施。

---

## 11. 安全规则

禁止：

* 输出密钥、token、cookie、私有证书。
* 把敏感信息写入日志。
* 把 `.env` 内容复制进文档。
* 提交包含密钥的文件。
* 绕过鉴权。
* 降低权限校验。
* 删除安全检查。
* 关闭 CSRF、CORS、认证、审计等安全机制，除非 spec 明确要求并说明风险。

如果发现敏感信息泄露风险，必须立即提示用户。

---

## 12. 高风险改动规则

以下改动属于高风险改动，必须先说明影响范围和风险，不要直接执行：

* 数据库结构变更
* 大范围数据更新
* 鉴权和权限逻辑
* 支付逻辑
* 删除逻辑
* 文件上传下载
* 导入导出
* 多线程或并发控制
* 缓存策略
* 队列任务
* 定时任务
* 部署脚本
* CI/CD 配置
* 公共 API
* 公共工具函数
* 全局配置
* 依赖升级

---

## 13. UI / 前端任务规则

涉及 UI、交互、页面行为时，必须说明：

* 修改了哪些页面或组件
* 用户如何操作
* 预期展示效果
* 边界状态
* 加载状态
* 空数据状态
* 错误状态
* 是否影响旧页面
* 如何人工验收

如果项目已有截图、E2E、Storybook 或 Playwright 测试，优先复用。

不得只说“代码已完成”，必须说明如何验证 UI 行为正确。

---

## 14. API / 后端任务规则

涉及接口时，必须说明：

* 接口路径
* 请求方法
* 请求参数
* 响应结构
* 错误码
* 权限要求
* 兼容性影响
* 是否影响已有调用方

修改已有接口时，必须优先保持向后兼容。

如果必须破坏兼容，必须明确说明原因和迁移方式。

---

## 15. Git 规则

允许：

* 查看 `git status`
* 查看 `git diff`
* 查看当前分支
* 给出建议 commit message

禁止自动执行：

* `git push`
* `git merge`
* `git rebase`
* 删除分支
* 强制覆盖用户代码
* 修改远程仓库配置
* 修改用户 Git 身份

每次完成任务后，建议输出 commit message：

```text
type(scope): message
```

示例：

```text
feat(auth): 添加登录速率限制
fix(api): 安全处理空响应
test(order): 为退款状态添加回归测试
docs(spec): 更新任务进度
```

---

## 16. 输出格式

每次完成任务后，必须按以下格式回复：

```md
## 总结

简要说明完成了什么。

## 修改文件清单

- path/to/file1
- path/to/file2

## 测试项

- command: result
- command: result

## 验证结果

说明是否满足 acceptance.md。

## 更新文件清单

- docs/specs/<需求目录>/progress.md
- docs/specs/<需求目录>/acceptance.md
- docs/specs/<需求目录>/notes.md

## 风险项

- 风险 1
- 风险 2
- 如果没有风险，写“暂无发现”。

## 提交建议

type(scope): message

## 下一步建议

建议下一步执行什么。
```

如果本次只做只读侦察，必须明确说明：

```md
## 总结

本次只做只读侦察，未修改业务代码。
```

## 17. 最终原则

本项目的默认工作方式是：

```text
需求先文档化
文档先 Draft
实现前 Frozen
任务要拆小
每次只做一项
先测试后实现
完成必须验证
结果必须记录
风险必须暴露
不做无关扩张
```

文档服务于执行和验收，不服务于形式主义。

Agent 应主动维护必要文档，但不得为了文档完整而制造大量无价值内容。
